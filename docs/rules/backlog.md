# Backlog правил — спорное, нерешённое, отложенное

Единственный файл спеки, которому разрешено описывать то, что **не решено**. Остальные описывают
правила такими, какие они есть.

**Правило, ради которого он заведён — [догадки запрещены](./README.md#жёсткое-правило-догадки-запрещены).**
Спека выведена из текста правил. Там, где текст допускает два прочтения, спека **не выбирает
удобное** и не «дорешивает по смыслу»: запись идёт сюда, а место в спеке помечается прямо в абзаце.
Догадка, записанная как правило, не остаётся догадкой: по ней пишут код, закрепляют тестом и потом
сверяются с ней как с источником.

**Где ещё смотреть.** Уже принятые решения по спорным местам —
[`2026-08-02-git-operations-rules-decisions.md`](../specs/2026-08-02-git-operations-rules-decisions.md);
открытые вопросы прошлых заходов —
[`2026-08-01-git-operations-open-questions.md`](../specs/2026-08-01-git-operations-open-questions.md).

## Формат записи

```
### Заголовок — в чём вопрос, одной строкой
**Что в правилах.** Формулировка, из-за которой возник вопрос — цитатой.
**Что непонятно.** Прочтения, каждое названо.
**Чем грозит.** Что сломается, если выбрать неверно.
**Где помечено.** Файл и раздел спеки с меткой «Не из правил».
**Статус.** `открыто` · `решено` (тогда ответ переезжает в спеку на место метки, запись удаляется).
```

## Открытые вопросы

### DDoS-заморозка и Rollback'овский replay-lock — блокируют ли карту Sudo от участия в комбо

**Что в правилах.** Запись Sudo ([`cards.md`](./cards.md)) говорит только «одновременно с картой,
у которой есть тег `sudo`» — про статус самой карты `support-sudo` (заморожена ли она DDoS'ом,
наложен ли на неё replay-lock картой `defense-rollback`) правила ничего не говорят.

**Что непонятно.** Два прочтения: (1) статус карты `support-sudo` не важен — важна только
принадлежность партнёра к тегу `sudo`; (2) карта Sudo, замороженная DDoS'ом или заблокированная
Rollback'овским replay-lock'ом, не может участвовать в комбо вовсе, как она не может быть сыграна
сама по себе.

**Чем грозит.** `onAttack` (`packages/engine/src/fake/attacks.ts:112-116`) проверяет для карты,
переданной как `action.combo`, только `partner?.id !== 'support-sudo'` — идентичность, а не
`frozen`/`replayLocked`. `combosFor` (`packages/engine/src/fake/project.ts`) зеркалит это же
поведение и не проверяет статус карты `support-sudo` в проекции. Если верное прочтение — второе,
движок сейчас пропускает ход, который по правилам должен быть запрещён.

**Где помечено.** [`cards.md`](./cards.md), запись Sudo (`support-sudo`).

**Статус.** `открыто`.

### Стоящий на столе релиз до оплаты цены — видят ли его соперники

**Что в правилах.** Запись Release ([`cards.md`](./cards.md)): «Цена. Сбросить одну карту с руки
по своему выбору (базовый режим)». Про то, что видно столу в промежутке между розыгрышем карты
Release и сбросом её цены, правила ничего не говорят.

**Что непонятно.** Два прочтения: (1) стоящий, ещё не оплаченный релиз виден только своему
владельцу — стол узнаёт о розыгрыше только в момент, когда цена оплачена и релиз встаёт в зону; (2)
релиз виден всем с момента розыгрыша, как обычно видна выложенная карта, а скрыта только его цена
до того, как она выбрана.

**Чем грозит.** Движок сейчас реализует первое прочтение: `discardForRelease`
(`packages/engine/src/fake/release.ts`) не эмитит ни одного события в момент розыгрыша — только
`onDiscardForRelease` (там же) делает это, по факту оплаты. Проекция (`pendingView`,
`packages/engine/src/fake/attacks.ts`) отдаёт `release` только владельцу пендинга; стол
(`apps/frontend/src/pages/board/[gameId]/_Board.tsx`) рисует стоящую карту в стадийном слоте тоже
только владельцу — у всех прочих доска остаётся молчаливой, пока не придёт `released`, и тогда уже
летит и релиз, и его цена одним движением. Если верное прочтение — второе, движок должен эмитить
что-то в момент розыгрыша, а не только по факту оплаты, и стол должен показывать стоящий релиз
всем игрокам, а не только владельцу.

**Где помечено.** [`resolution.md`](./resolution.md) §1, первый абзац.

**Статус.** `открыто`.

### Отказ нейтрализовать 503 при наличии способа — легальный ли это выбор

**Что в правилах.** [`resolution.md`](./resolution.md) §7: «Игрок выбывает единственным способом:
не нейтрализовал `trigger-error-503`».

**Что непонятно.** Два прочтения: (1) нейтрализация — обязанность, если способ есть: игрок,
владеющий Debugger'ом, Monitoring или подходящим релизом, обязан его применить, и отказ не
предусмотрен вовсе; (2) нейтрализация — право, а не обязанность: игрок волен отказаться и выбыть,
даже имея под рукой рабочий способ. §7 отвечает только на случай «способа не было», а не на «способ
был, но им не воспользовались по своей воле».

**Чем грозит.** Движок (`packages/engine/src/fake/triggers.ts`) не даёт отказа вовсе — пендинг
`neutralize503` принимает только один из `pending.methods`, ничего похожего на PASS. Сцена
плейграунда (`Error503Story.tsx`) устроена иначе: кнопка PASS у дока принимает `eliminate(true)` в
любой момент, пока пендинг открыт, независимо от того, есть ли у игрока способ ответить. Ветка,
которую сейчас видит стол в задаче #102 (`_useNeutralizeStaging.tsx`), отказа не даёт — как и
движок. Если верное прочтение — второе, движку нужен путь отказа; если первое — сцену плейграунда
нужно поправить, чтобы PASS был недоступен при наличии способа.

**Где помечено.** [`resolution.md`](./resolution.md) §7, после «Не нейтрализовал — выбывает.».

**Статус.** `открыто`.

## Спека отстаёт от кода

### Works on my Machine — код уже по новому правилу, текст спеки ещё по старому

**Что в правилах.** Владелец правил дал уточнение, отменяющее два из трёх ответов, по которым был
написан код в [#92](https://github.com/MythHand/ReleaseBoardGameP2P/pull/92)
([комментарий](https://github.com/MythHand/ReleaseBoardGameP2P/pull/92#issuecomment-5265618826)):
удар возвращается **по тому же типу релиза, по которому шёл**, — выбора у защищавшегося нет; и
отражённый Security Bug **никогда** не забирает релиз, а всегда отправляет его в сброс.

**Что непонятно.** Ничего — правило названо однозначно. Запись здесь только о рассинхроне.

**Чем грозит.** В спеке всё ещё написано старое прочтение: [`cards.md`](./cards.md) §184,
[`resolution.md`](./resolution.md) §90, §139, §140, §142 — «защищавшийся выбирает релиз в зоне
атакующего». Кто прочтёт спеку как источник, сочтёт код сломанным и «починит» его обратно.

**Где помечено.** Нигде: перечисленные абзацы принадлежат ветке владельца правил от #91, он
переписывает их сам. Правка отсюда затёрла бы его работу.

**Статус.** `открыто` — закрыть, когда ветка владельца от #91 вольётся: сверить перечисленные
абзацы с кодом (`packages/engine/src/fake/attacks.ts`, ветка `effect === 'reflect'`) и удалить эту
запись.

### Обязан ли игрок нейтрализовать Error 503, если он может

**Что в правилах.** Запись `trigger-error-503` ([`cards.md`](./cards.md)): «Игрок **выбывает**, если
не нейтрализует карту одним из трёх способов». Дальше идёт список способов — и ни слова о том,
обязателен ли способ, которым игрок располагает.

**Что непонятно.** Два прочтения: (1) формулировка описывает только последствие — не нейтрализовал,
значит выбыл, — и игрок вправе отказаться, даже держа Debugger; (2) нейтрализация обязательна, если
способ есть, и «выбывает» относится только к тому, у кого способа нет.

**Чем грозит.** Прочтения расходятся в игре, а не на бумаге: по первому игрок может выбыть
добровольно (например, партия уже проиграна, и он не хочет тратить Debugger), по второму такой ход
нелегален и движок обязан его отклонять. Доска всё это время показывала клавишу PASS в открытом
503 (`deriveDock` отдаёт `reaction` на своём пендинге), и каждое нажатие молча отклонялось: окна
нет, решение висит. То есть выбор уже был предъявлен игроку — просто не работал.

**Как сделано сейчас.** По первому прочтению: `onDecline503`
(`packages/engine/src/fake/triggers.ts`) банкует тревогу и выбывает игрока, PASS на своём 503
маршрутизируется туда (`reduce.ts`). Ровно то, что делает утверждённый источник — `Error503Story`
отправляет PASS в `eliminate(true)`. **Отдельный риск, не относящийся к прочтению:** PASS — та же
клавиша, которой заканчивают ход, и в открытом 503 она теперь необратимо выбывает игрока без
подтверждения. Промах стоит партии.

**Где помечено.** [`cards.md`](./cards.md), запись `trigger-error-503`.

**Статус.** `открыто`.

### Monitoring в зоне — выбор игрока или автоматика

**Что в правилах.** Запись `protection-monitoring` ([`cards.md`](./cards.md)): «Пока стоит —
`trigger-error-503` и `ai-crush-*` **игнорируются**: сбрасывается только угроза, Monitoring
остаётся». Запись `trigger-error-503` там же перечисляет стоящий Monitoring вторым из трёх
**способов**, которыми игрок нейтрализует карту.

**Что непонятно.** Два прочтения: (1) «игнорируются» — автоматика: 503 при стоящем Monitoring не
создаёт решения вовсе, игрока ни о чём не спрашивают; (2) это один из трёх способов, и игрок
выбирает его наравне с Debugger и жертвой релиза.

**Чем грозит.** По второму прочтению игрок, держащий и Debugger, и Monitoring, вправе сжечь
Debugger — по первому такой ход невозможен, потому что угрозы уже нет. Движок сейчас предлагает
все три способа сразу (`neutralizeOptions`, `packages/engine/src/fake/triggers.ts`), то есть
позволяет потратить карту против того, что и так игнорируется. Утверждённый визуальный источник
(`Error503Story`) отыгрывает первое прочтение: при Monitoring история не спрашивает ничего и не
зажигает тревогу вовсе.

**Где помечено.** [`cards.md`](./cards.md), запись `trigger-error-503`.

**Статус.** `открыто`.
