# Голосовой чат комнаты — дизайн #217

Дата: 2026-09-30. Задача: [#217](https://github.com/MythHand/ReleaseBoardGameP2P/issues/217).
Ветка: `feat/217-voice-chat`. Основа: `main` / `aa97ff53cc0170766877e7d350db219a3f0a0ee3`.
Статус: письменная спецификация согласована владельцем 2026-09-30 («продолжаем»). План реализации подготовлен для отдельного ревью; продуктовый код ещё не начат.

## 1. Цель и согласованные решения

Участники комнаты общаются голосом во время подготовки, партии и просмотра результатов. Целевой сценарий — до шести игроков и несколько зрителей. Голосовая сессия относится к комнате: переходы лобби → стол → результаты → лобби и следующая партия её сохраняют.

Владелец выбрал прямые аудиосоединения PeerJS. Игроки и зрители имеют одинаковые возможности говорить и слушать; боты в голосовом чате отсутствуют. Вход выполняется кнопкой наушников. При разрешении микрофон сразу работает; отсутствие устройства или отказ в доступе переводит подключение в режим «только слушать». Кнопка микрофона позволяет включить передачу позднее.

UI берётся из [PR #210](https://github.com/MythHand/ReleaseBoardGameP2P/pull/210): собственный микрофон, общая и индивидуальная громкость 0–200%, локальный mute участников и четыре состояния соединения. Собственный голос не воспроизводится. Параметры громкости и локальный mute независимы от выключения чужого микрофона.

По отдельному решению владельца все обращения за браузерными разрешениями основного приложения проходят через сервис в `apps/frontend` и функциональный декоратор `withPermission`. В текущем объёме это микрофон и существующая запись в буфер обмена. Сервис предусматривает добавление адаптеров для будущих разрешений без запросов неиспользуемых возможностей браузера.

Выход, исключение и смена комнаты освобождают ресурсы. При временном обрыве выполняется автоматическое восстановление. После перезагрузки страницы пользователь снова входит в голос кнопкой.

Детали протокола, отмены, таймаутов и границ модулей ниже конкретизируют согласованные решения и входят в предмет ревью этого документа.

## 3. Архитектура и границы

Игровые сообщения сохраняют звезду через хоста. Передача голоса образует отдельную mesh-сеть: одна двусторонняя `MediaConnection` на пару участников голосового чата. PeerServer обеспечивает сигналинг; пересылка и смешивание аудио браузером хоста не добавляются.

| Область | Ответственность и зависимости |
| --- | --- |
| `shared/lib/permissions/` | Типизированные адаптеры браузерного доступа, результат, наблюдение за состоянием при поддержке API, отмена и `withPermission`. Не зависит от комнаты, PeerJS, React или переводов |
| `network/transport/` | Media-обёртка над существующим `Peer`: звонок, ответ, закрытие, события потока/ICE и замена исходящего аудиотрека. PeerJS и прямые обращения к `RTCPeerConnection` остаются здесь |
| `network/voice/` | Протокол присутствия, проверка списка участников, выбор инициатора, жизненный цикл звонков, восстановление и защита поколений |
| `network/voice/audio` | Исходящий трек, тишина для слушателя, Web Audio-граф воспроизведения, локальные настройки и освобождение аудиоресурсов. Доступ к микрофону получает через сервис разрешений |
| `features/voice-chat/` | Преобразование состояния комнаты в props `@release/ui`, переводы и пользовательские команды. Не импортирует PeerJS и не запрашивает разрешения напрямую |
| Session composition / `useLobby` | Создаёт и уничтожает voice-runtime вместе с комнатой, передаёт актуальный transport, roster, идентичность и события выхода. Сохраняет прежний публичный контракт игры |
| Страницы лобби, Board и Stats | Размещают уже существующие голосовые блоки и передают callbacks копирования. Сетевые и аудиоресурсы не принадлежат странице |

Voice-модули используют явные интерфейсы roster, transport и доступа к микрофону; их можно проверить без настоящего браузерного микрофона. Выделение этих модулей не превращается в общую декомпозицию `useLobby` из #183.

## 4. Сервис разрешений и декоратор

`withPermission` — обычная типизированная функция высшего порядка, оборачивающая действие. Синтаксис `@decorator`, настройки экспериментальных декораторов и новые зависимости не требуются.

У каждого адаптера есть тип входных аргументов, проверка поддержки, вызов браузерной операции и тип результата. Успешный результат содержит ресурс или подтверждение выполненной операции. Декоратор передаёт этот результат обработчику успеха; например, voice-runtime принимает полученный `MediaStream`, а копирование подтверждает запись только после её завершения.

Результаты операций различаются как `success`, `denied`, `unavailable`, `unsupported`, `cancelled`, `timeout`, `failed`. Исходная ошибка сохраняется для диагностики. Отказ пользователя нельзя смешивать с отсутствием устройства, ошибкой захвата или отсутствием API. Ошибка самого обработчика успеха не классифицируется как отказ браузерного разрешения. Если обработчик не принял владение ресурсом из-за отмены или ошибки, адаптер освобождает его; успешная передача владения делает очистку обязанностью runtime.

Отдельный метод проверки состояния возвращает `granted`, `denied`, `prompt`, `unknown` либо `unsupported`. `unknown` означает отсутствие поддержки запроса состояния конкретного разрешения, а не запрет операции. Permissions API используется для информации и наблюдения, но успешность определяется самой операцией браузера. Решение браузера не кэшируется навсегда и не записывается в localStorage.

Два адаптера текущего объёма:

1. **Microphone.** Выполняет `getUserMedia` только для аудио, возвращает поток без повторного захвата внутри voice-runtime. Передача одного потока нескольким звонкам не вызывает новые permission prompts. Сервис не хранит и не владеет потоком после успешной передачи его runtime.
2. **Clipboard write.** Получает текст и выполняет `navigator.clipboard.writeText`. Само выполнение является операцией доступа: отдельный искусственный запрос разрешения не добавляется. Вызов происходит непосредственно из пользовательского click; перед ним нет обязательного асинхронного `permissions.query`, способного потерять user activation.

Для уже захваченного живого микрофона включение/выключение проходит через общий интерфейс доступа с повторным использованием активного ресурса, без нового `getUserMedia`. Если трек завершён, новый захват запускается только явным включением пользователем.

Каждая операция имеет владельца/поколение и поддерживает `AbortSignal`. Повторный click в рамках одной активной операции не запускает второе действие. Отмена отменяет принятие результата, даже если браузерный prompt физически нельзя закрыть программно. Поздно полученный отменённой или просроченной операцией поток немедленно останавливается и не передаётся обработчику. Поколение новой комнаты не получает результат старой.

При входе в голос ожидание ответа микрофона ограничено 30 секундами. После таймаута пользователь остаётся слушателем, а старый запрос становится недействительным. Браузерный prompt не объявляется закрытым: его поздний результат освобождается. Новый захват требует нового явного действия пользователя.

`CopyButton` получает callback `onCopy(text): Promise<boolean>` и показывает «скопировано» только при `true`. UI-библиотека не импортирует frontend-сервис и не выполняет скрытый обход через собственный `navigator.clipboard`. Callback передаётся через `LobbyCode` и его существующих потребителей в Lobby и Board; Stats сейчас не содержит такого контрола. Playground получает собственный адаптер копирования на уровне приложения; его самостоятельные инструменты не переносятся во frontend и не зависят от frontend-кода.

Браузерные запросы выполняются только в ответ на соответствующее действие пользователя. Возврат разрешения через настройки браузера обновляет информационное состояние, но сам по себе не включает микрофон.

## 5. Присутствие и управляющий протокол

Добавляются сообщения комнаты, которые проходят существующий валидируемый envelope:

| Сообщение | Направление и данные |
| --- | --- |
| `VOICE_JOIN` | Участник → хост: случайный `voiceSessionId` текущего входа и фактический `micOff` |
| `VOICE_LEAVE` | Участник → хост: `voiceSessionId` входа, который закрывается |
| `VOICE_MIC` | Участник → хост: `voiceSessionId` и новое фактическое `micOff` |
| `VOICE_ROSTER` | Хост → принятые участники комнаты: authority-generation, revision и полный список `{ memberId, peerId, voiceSessionId, micOff }` |

Хост выводит личность из актуального принятого соединения. Запрос не может выбрать чужой `memberId`, `peerId`, имя или роль. Хост применяет собственные действия тем же обработчиком локально. Дубликат join той же generation идемпотентен; leave/mic старого входа не меняют новый.

Получатели принимают roster только от текущего хоста. Authority-generation привязана к аутентифицированной host-сессии и сбрасывается при её замене; revision монотонна внутри неё. Имена и роли берутся из roster комнаты. `memberId` связывает отображение и локальные настройки, `peerId` адресует конкретное соединение, `voiceSessionId` отделяет новый вход в голос от старого при том же peer.

Снимок получает и человек, который не вошёл в голос: ему доступны число участников и их `micOff`. При новом допуске в комнату хост отправляет актуальный снимок. Громкость и локальный mute по сети не передаются.

При disconnect/kick/замене соединения хост удаляет соответствующую запись и публикует новый снимок. По нему остальные немедленно закрывают звонки удалённому peer. Клиент, получивший собственное исключение, также уничтожает локальный voice-runtime. Старый peer не остаётся получателем голоса после удаления из принятого roster.

Смена роли player ↔ spectator и обновление имени меняют отображение, но не голосовое членство. Изменение роли не создаёт новый звонок.

## 6. Прямые звонки и режим слушателя

Детерминированный инициатор каждой пары — участник с лексикографически меньшим `memberId`. Он создаёт звонок только после подтверждения обеих voice-записей хостом. Это устраняет два одновременных звонка между одной парой.

Metadata содержит версию voice-протокола и voice-session IDs обеих сторон. При входящем звонке проверяются `call.peer`, текущая запись комнаты, канонический voice-roster и обе generation. Неизвестный или устаревший звонок закрывается без передачи микрофона. Доверие не строится на имени или `memberId`, присланном вызывающим в metadata. Если сигналинг опередил roster, закрытый вызов будет повторён инициатором после получения актуального снимка.

Для каждой стороны заранее существует ровно один исходящий аудиотрек. При доступном микрофоне это захваченный аудиотрек; для слушателя — синтетическая тишина из `MediaStreamAudioDestinationNode`, не подключённая к акустическому выходу и не использующая устройство ввода. Обе стороны передают такой stream при `call` / `answer`, чтобы согласованный звонок имел аудиоканал в обоих направлениях.

Не полагаемся на звонок с пустым stream без аудиотреков: для последующего включения микрофона ему может потребоваться новая SDP-negotiation. Вместо этого transport меняет существующий sender на реальный трек через `RTCRtpSender.replaceTrack`. Эта операция остаётся внутри transport. Отказ замены закрывает и восстанавливает только соответствующий звонок; остальные участники продолжают слышать друг друга.

Выключение микрофона немедленно прекращает передачу содержимого захваченного трека через `track.enabled = false`; фактический `micOff` публикуется хосту. Пока человек остаётся в голосе, живой захваченный трек допускается сохранять для повторного включения. Это действие mute; полное освобождение устройства гарантируется при выходе из голоса/комнаты. У слушателя микрофонный трек отсутствует и `micOff = true`.

При завершении трека, отзыве разрешения или потере устройства исходящий sender переключается на тишину, `micOff` становится `true`, а прослушивание продолжается. Новый доступ — только по кнопке микрофона через декоратор.

Все звонки используют текущий `Peer` и его существующую конфигурацию PeerServer/STUN/TURN. Второй peer с отдельной авторизацией не создаётся. Ошибка MediaConnection сама по себе не переводит игровую сессию в fatal error и не закрывает DataChannel.

## 7. Звук и локальные настройки

Для чужого потока граф выглядит так: `MediaStreamAudioSourceNode → participant GainNode → master GainNode → destination`. Собственный поток к destination не подключается.

Обе громкости — проценты 0–200, по умолчанию 100. Эффективное усиление равно `(participantVolume / 100) * (masterVolume / 100)` и достигает 4. Локальный mute устанавливает gain участника в 0, сохраняя его выбранный процент. Ползунок изменяется и при mute; unmute восстанавливает последнее значение. `micOff` собеседника отображает его собственное состояние передачи и не меняет локальный mute.

Один voice-runtime владеет AudioContext, звонками, узлами воспроизведения и исходящими треками. AudioContext создаётся/resume запускается из пользовательского входа в голос до ожидания микрофонного prompt. Автоматический autoplay не предполагается. Если браузер снова требует пользовательского действия для звука, состояние прерывается и показывается локализованная подсказка выйти и подключиться снова кнопкой наушников; скрытого состояния «подключён, но нельзя услышать» не должно быть.

Настройки хранятся локально в памяти комнаты по `memberId`: сохраняются при смене экранов, временном обрыве, новом peerId и выходе/повторном входе в голос в той же комнате. Полный выход из комнаты или reload сбрасывает их. Настройки и факт желания говорить не сохраняются в session persistence.

## 8. Состояния, восстановление и очистка

| Состояние | Условие и действие кнопки наушников |
| --- | --- |
| `off` | Пользователь не вошёл в голос; click запускает вход |
| `connecting` | Первый вход: подготовка звука, запрос микрофона, подтверждение roster и первые звонки; повторный click не создаёт вторую попытку |
| `connected` | Членство подтверждено, вывод звука готов, ожидаемые парные соединения установлены. В одиночку состояние достигается без звонков. Click выходит |
| `interrupted` | Уже начатая голосовая сессия потеряла управляющую связь, возможность воспроизведения либо ожидаемый аудиоканал; сохраняет настройки и автоматически восстанавливается. Click выходит |

При новом участнике уже активная сессия устанавливает дополнительный звонок. Существующие рабочие каналы продолжаются. Если новый ожидаемый канал не готов за 15 секунд или завершился с ошибкой, локальное состояние становится `interrupted`. Уход участника удаляет ожидание; пустая комната сама по себе не является обрывом.

Для потерянного звонка после grace-периода 2 секунды выполняются до пяти автоматических попыток с задержками 1, 2, 4, 8 и 15 секунд. Пока соединение отсутствует, остальной голос работает. После исчерпания попыток состояние остаётся `interrupted`; существующая кнопка позволяет выйти и повторно войти. Новая подтверждённая generation peer/voice-сессии или восстановление транспорта комнаты создаёт новую серию. Новые prompts микрофона таймеры восстановления не вызывают.

При восстановлении управляющего соединения сначала завершается admission комнаты. Пользователь, который оставался в голосе в этой же странице, повторно объявляет voice-присутствие с новой generation; его громкости и намерение mute сохраняются. Старые voice IDs из persisted lobby/keeper snapshot не считаются активными. После reload runtime начинается с `off` даже при восстановленной игровой комнате.

При смене подтверждённого host-контекста runtime обновляет источник roster. Новый хост собирает присутствие повторными объявлениями принятых участников; живые парные звонки сохраняются только при сохранённом актуальном членстве. Само изменение роли host/player не запрашивает микрофон. Текущий transferHost передаёт намерение, но не реализует завершённый handoff: проверяем границу смены контекста, не объявляем настоящую миграцию работающей и не добавляем её в эту задачу.

При потере подтверждённой собственной сессии комнаты передача микрофона приостанавливается до повторного admission. Исключение, отклонённый reconnect, явный выход или замена комнаты завершают voice-вход, а не запускают новый автоматический допуск.

Каждое асинхронное действие сверяет room-generation, transport-generation и voice-generation до принятия результата. Заменяемый звонок дополнительно имеет собственное поколение. Поздние stream/error/close и разрешения старого владельца не меняют новую сессию.

Teardown идемпотентен: отменить запросы и таймеры, отписать callbacks, закрыть media connections, отсоединить узлы, остановить микрофонные и синтетические треки, закрыть принадлежащий runtime AudioContext и очистить текущий voice-roster. При выходе только из голоса игровой transport не уничтожается; при выходе из комнаты его закрывает прежний room lifecycle после очистки голоса.

Ошибки голоса и разрешений отображаются в области голоса существующим UI-паттерном и переводами EN/RU. Отказ/отсутствие микрофона объясняет режим слушателя; ошибка аудиосвязи не маскируется сообщением об отказе permission и не ломает игру.

## 9. Подключение UI

- **Лобби:** строка `VoiceChat` над текстовым чатом, как в `LobbyChatStory`. `_LobbyView.tsx` реализует размещение по эталону, а не импортирует экран Lobby из UI.
- **Стол:** отдельная квадратная вкладка между settings и текстовым чатом, `VoiceTabIcon` с актуальным `status` и `micOff`, панель `VoicePanel` шириной 420px. Поведение одинаково на столе игрока и зрителя из #214.
- **Результаты:** slot `Stats.voice` и существующая копия заголовка `stats.voiceChat`, как в `StatsChatStory`.
- Props всех трёх блоков берутся из одной модели. Собственная строка определяется `selfId = memberId`; `guest` преобразуется в UI-роль `spectator`. Счётчик показывает voice-roster, а не число всех игроков комнаты.
- Контролы громкости и своего микрофона доступны в состояниях `connected` / `interrupted` по контракту #210. Громкости не исчезают при обрыве; mute и `micOff` независимы. Цвета, подсказки и порядок участников сохраняются из итогового #210.

Новые сообщения об отказе, слушателе и ошибке добавляются в обе локали. UI остаётся i18n-agnostic; frontend использует `@release/translation`. CSS Modules, токены и Typography сохраняются. Новые панели настройки устройства, индикаторы говорящего и push-to-talk в объём не входят.

## 10. Проверки и критерии приёмки

1. **Permissions.** Success/denied/unavailable/unsupported/failed, неподдерживаемый query при работающем API, явный повтор после изменения permission, повторный click, отмена/таймаут и остановка позднего потока. Успешный захват не повторяется внутри действия. Clipboard без предварительного await, успех/отказ и отсутствие ложного «скопировано».
2. **Протокол.** Допуск voice только принятым peer, host authority, idempotent join, stale leave/mic/roster, новый voiceSessionId при том же peerId, снимок для не вошедшего в голос, исключение и замена peer с устойчивым memberId.
3. **Media.** Одна MediaConnection на пару при одновременном входе, обоих порядках соединения слушателя и говорящего и двух слушателях; последующее включение микрофона, смена трека, восстановление одного звонка и отсутствие влияния его ошибки на игровой transport.
4. **Audio.** Отсутствие self-loopback, общий и индивидуальный gain 0/100/200, максимальное произведение 4, mute с сохранением изменяемого процента, отсутствие проигрывания нескольких копий одного чужого потока.
5. **Lifecycle.** Игрок/зритель/хост, поздний вход, смена роли, экраны и rematch, временный обрыв, новый peerId, существующая смена хоста, reload с voice off, kick и отказ admission. После teardown нет живых своих треков, таймеров, звонков, узлов и активных callbacks.
6. **UI.** Сравнение реального frontend с `LobbyChatStory`, `TableChatStory` и `StatsChatStory`, четыре состояния и mute. Для Board использовать реальный `/debug.html` с игроком и зрителем, а не ограничиться unit-тестами. Проверить отсутствие перекрытий с chat/settings rail.
7. **Настоящее аудио.** Отдельные браузерные контексты хоста, игрока и зрителя: речь в обоих направлениях, отказ микрофона у одного, слушатель подключается первым и последним, включение позднее, mute/200%, сетевой обрыв, исключение и переходы экранов. Проверить как минимум Chrome и Firefox; после этого прогон целевой комнаты с шестью игроками и несколькими зрителями, например двумя.
8. **Регрессии.** До продуктовых изменений зафиксировать baseline, затем целевые тесты permissions/network/features/UI и `pnpm test`, `pnpm typecheck`, `pnpm lint`, `pnpm build`, `git diff --check`. Проверить REUSE для добавленных файлов. Реальный аудиопрогон, mock-тесты, UI debug и проверки исходной базы отражать отдельно.

Реальное WebRTC-подключение в #214 осталось неподтверждённым из-за ICE. Поэтому его старые результаты нельзя использовать как подтверждение работоспособности голосового mesh. Не менять VPN, DNS, TURN или окружение без диагностики конкретного отказа. Если окружение препятствует сетевому прогону, фиксировать точную стадию и оставлять этот критерий приёмки неподтверждённым.

## 11. Объём и технические ограничения

Общий сервис разрешений и маршрутизация существующего clipboard-доступа входят в задачу по явному запросу владельца. Общий рефакторинг сети, изменение движка/правил, запись разговоров, видеосвязь, SFU/медиасервер, новые TURN credentials, модерация микрофона хостом и отдельный voice-лимит не добавляются.

Для N участников mesh содержит до `N * (N - 1) / 2` парных соединений, каждый браузер отправляет трек до N−1 адресатам. Это цена выбранной схемы для небольшой комнаты. Существующая квота 28 зрителей не является обещанием качества конференции из 34 человек; такую нагрузку требуется отдельно измерять, не вводя незаявленный продуктовый лимит.

Синтетический трек, `replaceTrack`, пользовательская активация AudioContext и реальные ICE-соединения подлежат браузерной проверке. Если установленная версия PeerJS или браузер не позволяет заменить трек, предусмотрен адресный новый звонок с сохранением локального voice-входа. Новые продуктовые зависимости не предполагаются.
